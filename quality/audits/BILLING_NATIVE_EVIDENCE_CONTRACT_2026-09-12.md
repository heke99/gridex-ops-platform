Use one private/service-callable assertion with internal callers selecting an explicit finite phase. Proposed shape (names reviewable; semantics required):

  p_company_id uuid,
  p_underlay_id uuid,
  p_pricing_run_id uuid,
  p_phase text,                  -- calculate | lock | reserve | dispatch | replay

Null company/underlay or unknown phase fails 22023. Run is mandatory outside calculate. Helpers need fixed trusted search_path, schema qualification and null-safe role checks where exposed. Revoke PUBLIC/anon/authenticated; do not expose a caller-controlled phase that can turn a new write into historical replay. `replay` is only valid when the exact operation already exists and its immutable seal/operation identity can be verified. An assertion with no caller integration is not a guard.

Canonical manifest v1 should record company/underlay/customer/meter/contract, exact snapshot ID and canonical snapshot hash, applicable plan/product version references, currency, area/direction/settlement, civil and original instant bounds, source count and total kWh, ordered item/source/revision/value records, and ordered interval evidence plus frozen selected price identity/value. Add calculation line/result digests and the documented rounding/evidence format version. Exclude mutable projection statuses, latest pricing-error annotations and updated_at. Hash a defined canonical PostgreSQL JSONB representation; persist enough content to independently explain/recompute the digest. A digest of counts alone is insufficient against same-count substitutions.

A small immutable seal keyed by `(company_id,pricing_run_id)` is preferable to altering a locked run via maintenance to attach evidence. Proposed relation `billing_pricing_evidence_seals`: company/run/underlay composite relationships, manifest JSONB, manifest_sha256, version, sealed_at; unique company/run; INSERT only by guarded lock path, ordinary UPDATE/DELETE rejected. This permits an explicitly validated legacy locked run to receive a seal without relaxing the existing locked-run guard. The naming/storage choice is not a requirement for a standalone rule table: this seal records the accepted billing calculation's evidence.

For new successful calculations, preserve a server-verified candidate fingerprint in run metadata before locking, or carry the complete candidate manifest in `p_result.billing_evidence_v1`. It must bind the result to the input snapshot actually used. SQL revalidates against authoritative rows in the persistence transaction; a freshly changed but still-valid source with the same total cannot be paired with an older calculated result. Existing RPC signature can remain unchanged by adding the payload field, but runtime compatibility must be coordinated. Missing descriptor must not silently become “verified”; legacy admission is a separate explicit checked path. Do not persist a caller fingerprint without recomputing/validating it.

### Canonical evidence checks

1. Live calculate/first-lock/new reserve: source status validated, readiness ready, readiness_issues an empty array, missing count exactly zero, no billing blocker; pricing-pending flags/latest failed pricing errors are not source blockers. Validate exact tenant/customer/meter/contract/supply/snapshot/area/direction/settlement links. Snapshot must exist for that contract/company; require its canonical hash/content match. Applicable component rule content suffices without invented tax/fee IDs.
2. Resolve segment instants from payload billing_period_start_instant/end_instant, checking their Stockholm civil dates equal persisted civil dates. Without original instants, interpret civil midnight in Europe/Stockholm. Reject missing/invalid/null/inverted bounds; do not widen a midmonth segment to a whole month. Accept valid original intraday boundaries. Legacy run timestamptz dates can be compared by canonical Stockholm civil bounds while coverage uses true segment instants.
3. Query the **entire** item set in PostgreSQL, no API page/limit. Positive integer authoritative source count equals item count and unique normalized-source count. Every item has matching tenant/customer/meter/contract/area/flow, ready_for_pricing, empty warnings, real canonical source/raw/message/supply identities and appropriate revision evidence. Compare saved original revision/value linkage against the normalized source at first acceptance; source ID presence alone is inadequate.
4. Ordered by start/end/id, require exact contiguous coverage from segment start to end, no duplicate/overlap/outside/invalid interval. Verify quantity with unit conversion, zero intervals allowed within a positive total, total kWh difference at most 0.001. Clipped underlay items must reconcile proportionally to the original source bounds/quantity and direction; do not require each clipped quantity equal an uncut source row. Preserve positive production/correction quantities and separate settlement sign. Validate actual product/register/channel grouping semantics rather than inventing one interval series across legitimately distinct flows.
5. Determine interval evidence requirement from the immutable selected pricing components/resolution and flow, not optional caller flags. Hourly/quarterly positive spot weight for non-production requires one evidence row for each underlay item. Fixed/monthly and production rules that legitimately have no interval evidence remain valid. If any interval evidence is supplied, validate it completely even if not mandatory for the chosen branch; do not accept arbitrary orphan extras.
6. Each evidence row matches exact company/run/underlay/item/contract/area/flow, period bounds, hour/quarter resolution, consumption within 0.000001 and finite price/amount; unique item linkage and full set equality. Check selected source ID exists and matches period/area/resolution/source policy at acceptance, or a complete immutable selected-price source record provides equivalent proof. Source-price mutable updates after freezing do not rewrite historical evidence. New price/consumption candidates must be validated under coordinated source locks or a stable source-version/fingerprint, not a naked earlier application read.
7. Amount per evidence row follows the existing spot weight and rounding convention. SQL numeric rounding differs from JS Math.round at negative halves; define/test parity explicitly. For finite decimal inputs the JS half-up-toward-positive rule can be specified as floor(value*100+0.5)/100, with floating-versus-exact-decimal limits tested. Do not silently switch to PostgreSQL round for negative spot prices. Full raw weighted source sum versus base line uses the original whole-quantity calculation; the sum of per-interval rounded amounts need not equal the single rounded aggregate. Record/assert the intended residual rather than reject valid intervals by an invented equality.
8. Validate pricing lines are nonempty for accepted pricing, exact run/underlay/company, finite quantities/rates/amounts, expected base lines and relevant canonical component inputs. Require stored run totals equal summed line net/VAT/gross within existing monetary tolerance. This is not a full new tariff engine; targeted missing/extra/altered monetary evidence must fail, while fixed/monthly and credit controls remain valid.

**Digest compatibility:** current SQL hashes `(incoming x || {pricing_run_id})::jsonb::text`, where x includes a client evidence_sha256 and can include extra keys. The persisted row does not retain that original x verbatim. Therefore its existing digest cannot generally be recomputed by hashing `to_jsonb(stored_row)`; that would be a false check. For new evidence define/persist a canonical input subset or separate versioned manifest digest and test the exact projection. Preserve historical digest bytes; legacy seal admission validates durable row values/full identities and declares its format, without pretending to have reconstructed missing old input JSON. Provider invoice snapshots refer to the persisted evidence SHA and must keep those exact identities.

## Lock order and mutation discipline

Existing persist and lock have opposing row order (underlay→run scan/write versus run→underlay). Unify native entrypoints before adding more locks:

1. Operation/batch idempotency mutex if applicable; then all affected company/underlay mutexes and underlay rows in sorted UUID order; then pricing-run rows sorted; then export item/portal rows and side effects. A first read of a run only to discover underlay is untrusted: reload/revalidate it after acquiring locks. Never take run row first and then underlay in one path while another does the reverse.
2. Every item/preview-line/interval-evidence writer must serialize on the same underlay parent before altering its economic contents, including INSERT (phantom row), UPDATE, DELETE and owner RPCs. Add narrow triggers enforcing parent synchronization/freeze, or revoke/direct all applicable writes through guarded routines with equivalent enforcement. Current service-role table access makes caller-only conventions insufficient.
3. Under the parent lock, validate child sets without unnecessarily locking child rows in the opposite order. A direct UPDATE may already hold a child tuple before its BEFORE trigger seeks the parent. Locking all child rows after parent while that writer holds a child and waits for parent can deadlock. Prefer parent-mediated write serialization plus stable reads, with sorted multi-parent mutation rules. Any unavoidable deadlock must abort cleanly/retry as a whole; tests must never report a half-completed success.
4. Source normalized revisions and selected market-price reads need a defined consistency boundary too. At first acceptance lock/recheck the source rows in a documented stable order, or integrate source-version changes with the parent assertion/fingerprint. A PostgreSQL function issuing multiple SELECTs under READ COMMITTED is not automatically one immutable source snapshot. Prove source update-before/after-acceptance outcomes explicitly.
5. Once sealed, prohibit edits/deletes/new children that would change sealed underlay/line/evidence economics, referenced immutable snapshot content or the seal. Permit only operational projection fields, provider reconciliation, retry metadata and separately reviewed maintenance that cannot rewrite dispatched history. New normalized metering revisions remain allowed: they create correction history and do not alter the accepted frozen item evidence. An existing normalized row becoming replaced does not invalidate replay of its historical invoice.
6. Regeneration attempts on a frozen underlay must not delete/reinsert items with fresh IDs. The current interval-evidence FK already rejects deleting referenced items, but fixed/monthly pricing needs the same deliberate freeze. Exact no-op writer replay can return the existing underlay after comparison; a changed regeneration requires a new/reopened permitted calculation scope with old history retained. Do not invent a corrected-underlay creation path or silently bypass the segment uniqueness constraint.
7. Unlocking a period does not grant permission to mutate an evidence seal or provider-confirmed invoice. Permit controlled unsealed/undispatched recalculation only; if the current generic unlock RPC can mutate reserved/sent histories, constrain it within the reviewed patch or keep that gate explicitly open. Preserve all existing maintenance audit semantics; no blanket maintenance/GUC bypass should be added.

## Minimal send reservation/fencing interface

Existing provider fields (`provider_idempotency_key`, `provider_request_id`, `request_payload`, confirmed GUID/status and uncertainty fields) can hold the stable provider identity/request. Add an immutable dispatch evidence binding (seal ID/hash + exact request hash + approved calculation hash) and a claim token/attempt receipt only where existing attempt fields cannot express fencing. gridex_reserve_approved_invoice_dispatch_v1(
  p_company_id uuid, p_export_item_id uuid,
  p_expected_approval_hash text, p_request_payload jsonb,

gridex_finish_reserved_invoice_dispatch_v1(

It verifies request identity/currency/principal/VAT/rounding and stable pricing reference against the sealed graph; fixed invoiceDate/dueDate become part of the first reservation and are reused on retry rather than regenerated. Returned payload/hash/key are the only allowed provider request. Token cannot authorize a different request. Exact existing reservation/confirmed result returns its stable identity; conflicting payload/approval hash fails.

Reservation commit is the **linearization point** of which immutable evidence authorizes this external operation. A correction accepted before first reservation must be detected/reviewed; one arriving after committed reservation does not rewrite the authorized request or retrospectively mutate a sent invoice. Its correction workflow is separate. If the product instead requires cancelling a committed reservation before HTTP whenever any later source changes, that requires a stronger coordinated cancellation protocol; a final JavaScript reread cannot promise it. Do not claim that an expiring process lock prevents an already running worker from making HTTP calls.

Finish matches current token/request hash and persists export/portal/run/legacy/attempt results atomically, preserving higher provider-event projections (see BILL03 contract). Confirmed GUID identity is immutable; stale token writes have no effect. Unknown transport outcome keeps immutable reservation and uses provider reconciliation before retry, not a fresh reference. Capway's existing externalReferenceCode reconciliation stays in force; factoring purchase replay is not proven by this SQL. HTTP exactly-once cannot be created by database locks alone. No database transaction may span provider HTTP.

## Integration addendum — common event/dispatch lock order (2026-09-12)

This supersedes the earlier event→item→portal→trigger lock-order wording. Source-backed feasibility: **yes, for the coordinated RPC paths**, with candidate discovery followed by locked identity revalidation. It is a design requirement, not executed native evidence or a guarantee for arbitrary direct DML. Skill routing: receiving-code-review and verification-before-completion apply to this bounded correction; existing Supabase source discipline applies. No implementation, full audit, UI/performance work, delegation or live access is involved.

- `20260702150000_gridex_sent_invoice_protection.sql:8–76` freezes item `billing_underlay_id`, `pricing_run_id` and customer/financial fields only when **OLD.status is sent/credited**, with the existing maintenance escape hatch. It does not establish universal immutable mapping for pending, failed, cancelled or disputed rows. `20260820113132_invoice_export_locked_pricing_guard.sql` checks the referenced run is same-company and locked on insert or company/run update; it does not freeze the mapping. July27 `gridex_enforce_customer_contract_chain_v1` and its registrations check compatible customer/contract/underlay identities with ordinary reads, without obtaining the common parent lock. Therefore the first item lookup must be treated as untrusted discovery even when ordinary sent-item mapping is protected.
- `20260826213000_invoice_review_projection_sync.sql:8–67` registers `customer_invoices_underlay_projection_v1` AFTER portal INSERT or specified-column UPDATE. Its ordinary item lookup derives export_run_id, then its underlay UPDATE acquires the underlay row lock. Portal BEFORE chain/portfolio/reference guards and row writes precede this AFTER effect. The August16 `customer_invoices_partner_api_events_v2` is another AFTER trigger; for the same applicable event its name sorts before the underlay projection and can create domain/delivery effects first. Preserve both full bodies and registrations; do not rely on moving or disabling triggers to avoid the inversion. All effects still roll back together.

Required sequence: (1) apply locks/fences its **one event row first**, as today’s separate claim/reclaim protocol requires; completed-receipt and event-only rejection paths can return without graph locks. (2) Read the exact candidate item without a row lock solely to discover company/underlay/run IDs. (3) Acquire the same company/underlay mutex and underlay row lock used by persist/lock/reserve/finalize; acquire the referenced pricing-run row next only when needed. (4) Lock the item, reload it and revalidate event item ID/company/provider/environment/GUID plus underlay/run/customer/contract binding against the locked parents. (5) Lock/upsert the portal and require its company/item/underlay/customer/contract aliases match this exact graph; a merely same-customer alternative underlay is insufficient. Then perform projections and existing domain/outbox/completion writes.

If discovery changed, fail/retry the **whole transaction**, with no business writes/completion; never discover a different underlay while holding the item and acquire that parent out of order. Missing canonical parent becomes an explicit review/error outcome. Dispatch has no event-row prefix and uses underlay→run if needed→item→portal. Neither dispatch nor graph/trigger helpers may acquire a provider-event row after taking graph locks. Sorted parent acquisition applies to batches. Existing generic direct portal/status writers are outside this coordinated guarantee until routed through the same boundary; a new portal trigger that first takes an item/underlay lock after the portal write would not establish the required order.
