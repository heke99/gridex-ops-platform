## Point 82 refinement: durable rule content is sufficient without standalone IDs

The original matrix was too strict where it treated absence of `tax_rule_id`, `fee_rule_id` or a rule FK on every line as missing traceability. The user requires derivation to a rule. An immutable, identifiable snapshot containing the complete rule, connected to recorded inputs/results and the pricing engine version, can provide that derivation. This is accepted as a valid existing representation, not a proposed schema change.

**Actual freeze/hash/link chain:**

1. `lib/pricing/contractPricingVersioning.ts:addComponent` serializes component code, amount, calculation type/base, unit, inclusion/visibility and VAT applicability. `parseOptionalFeeLines` validates custom fee label/amount/unit and records lifecycle, billing frequency, calculation base, `vat_treatment` and `vat_applicable`; its component key can identify a position/content in the snapshot rather than an external rule row. The returned contract snapshot includes component arrays, validity and VAT rate/fraction.
2. `offerQuote.ts` selects frozen base/price arrays and retains exact selected component references and VAT rate. `customerApplicationOnboarding.ts` copies those arrays into both snapshot columns and snapshot_json, together with plan/version, selections and contract context. Canonical signing and signed-document import SQL also insert snapshot arrays/JSON and attach the resulting snapshot ID to the contract. These are preserved rule definitions, not just totals.
3. Latest `20260901151000_canonical_contract_price_area_binding_schema.sql:gridex_fill_contract_price_snapshot_binding_v1` writes the actual component column arrays and canonical version/area bindings into snapshot_json before insertion. Its `aab_...` trigger clears the caller hash so the later `zzzz_contract_price_snapshots_hash_integrity_v1` computes it after normalization. `20260823204821_enforce_contract_price_snapshot_hash_integrity.sql` hashes canonical `snapshot_json::text`, requires non-null 64-hex hash, and rejects nonempty mismatches at its boundary. July 2 snapshot mutation guard blocks ordinary UPDATE/DELETE; explicit maintenance is a separate path. Therefore the latest normal insertion path binds component arrays into the hashed content; absence of a separate line-level rule ID does not break this chain.
4. Pricing engine loads the exact snapshot by company, snapshot ID and contract ID, merges its JSON and component arrays, then `resolvePricingConfiguration` uses the frozen components instead of mutable tenant fee tables for a billable underlay. The calculator's line includes input_amount/input_unit, calculation_type/base, selection/lifecycle metadata, actual quantity/unit price/net amount, effective VAT rate/VAT/gross and sort order. `gridex_persist_pricing_run` stores those complete line outputs and interval evidence with pricing-run/underlay identities. It does **not** persist a separate full input snapshot on the pricing_runs row: its own metadata is source=pricing_core, atomic=true. The frozen contract snapshot and underlay links are therefore material to derivation, not optional documentation.
5. `invoiceReviewPrepare.ts:buildCalculationSnapshot` records exact snapshot ID/hash/schema, contract and pricing version references, `pricing_run_id`, `pricing_engine='pricing_core_v1'`, period/quantity, pricing lines, interval evidence and totals. Its stable-key JSON serializer hashes the full calculation object with SHA-256. The invoice stores that object/hash; the legacy payload snapshot also stores underlay/contract/pricing/calculation. Locked-run and sent-invoice protections already exist. `pricing_core_v1` is the recorded algorithm-version identifier; it is not a per-release source-code digest, and this review does not invent a requirement for one.

**Concrete derivability:** a frozen custom fee of SEK100, fixed_once, quantity1, standard VAT and snapshot rate0.25 yields net100/VAT25/gross125 under the recorded calculator rules. The same frozen rule with vat_treatment=exempt/vat_applicable=false yields VAT0. A monthly fee records its amount, month quantity and explicit proration policy; a per-kWh fee records original ore/SEK unit and consumption basis; a percentage fee records its calculation base and percentage. Snapshot-level identity plus this content is sufficient to explain the rule even when `component_reference` is null. These examples illustrate the inspected formulas; no new synthetic/native run was performed in this refinement.

**Genuine remaining gaps, without a new ID requirement:**

- BILL01/02 still prevent an all-components/all-consumption completeness claim. Rule content cannot repair a missing price/consumption page or an erased blocker.
- Normalization drops malformed component rows and unknown calculation types produce warnings; missing required rule content must be distinguished from a legitimately excluded/nonapplicable component. The matrix does not yet prove all mandatory selections survive every creation/import path.
- When VAT is present in the frozen snapshot, its rate and exemption treatment are derivable. When the rate is absent and resolution reads mutable contract VAT or uses the documented 25% engine default, line outputs preserve the applied rate but do not explicitly label the source branch. A default is itself a rule; missing branch provenance is only material where original permitted policy inputs cannot otherwise be recovered. Verify a real fallback case and contract timing before promoting a defect. Do not call every missing frozen rate untraceable merely because no tax-rule ID exists.
- Native tests must verify the real trigger ordering, normalized-content hash, immutable snapshot/run behavior, correct company/contract/version links and preservation of the full calculation snapshot. Existing source guards are accepted evidence, not an executed database proof. Hash presence alone is not an independently replayed derivation or recomputed-hash gate.
- For non-VAT taxes, establish applicable rule content or nonapplicability in the contract being tested. This refinement neither asserts a universally required energy-tax line nor supplies statutory policy that was absent from the task.

The new source evidence therefore upgrades custom/fixed-fee and VAT **rule representation/derivability** to source supported for the complete frozen path. Overall point 82 remains partial for completeness and native integrity reasons; a missing standalone rule identifier is removed from the rejection criteria.
