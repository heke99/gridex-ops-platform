## Three control views: exact decision

The finite scope is `gridex_automation_control_center_v`, `gridex_batch_2b_live_control_tower_v` and `gridex_batch_2c_control_tower_summary_v`. Each adds authenticated SELECT plus seven non-SELECT privileges relative to the retained reference. Each remains an ordinary joined view with security_invoker=true and unchanged definition; none has an INSTEAD OF trigger or non-SELECT rule in the retained schema.

**Decision: no source-qualified corrective view migration is established. Preserve the authored invoker definitions and leave these ACLs out of the inbound service-only repair. This is a bounded no-patch decision, not effective-role equivalence, approval of trigger installation, or a schema acceptance exception.** The following evidence explains both the preservation decision and its limits.

### What the migrations expressly authorize or restrict

- The original automation view is created in `20260521_batch_1_2_live_readiness_and_automation_hardening.sql:241–273`; batch2b labels its definition “Live operations Control Tower view” at `20260521_batch_2b_full_automation_and_live_ops.sql:238–255`; batch2c creates the summary at `20260521_batch_2c_end_to_end_operations.sql:431–447`. These sources define a monitoring projection, with no explicit authenticated SELECT-only or service-only ACL contract.
- `20260611150000_launch_readiness_security_routes_stats.sql:140–161` and `20260611170000_launch_readiness_completion_db_warnings_retention_bulk.sql:143–160` expressly harden the automation view with security_invoker and anon REVOKE, leaving authenticated outside those revocations.
- More decisively for all three, `20260611190000_launch_linter_hardening_security_definer_rls.sql:115–139` loops over every public ordinary view, sets security_invoker, and revokes PUBLIC and anon. It does **not** revoke authenticated or narrow it to SELECT. This establishes the source's chosen role/RLS boundary; it does not prove that the author considered every non-SELECT privilege.
- `20260822224708_canonical_ediel_production_projection_convergence.sql:168–243` replaces all three projections with joins to canonical ediel_production_state. `20260904120000_canonical_tenant_invariant_convergence.sql:62–64` explicitly restores security_invoker=true on all three. Its separate service-only assertions at 25–47 name only the three inbound tables, not these views.
- The existing executable invariant `scripts/sql/tenant-isolation-invariants.sql:154–168` requires every public ordinary view to be security_invoker. It neither requires SELECT-only view ACLs nor checks TRIGGER/locking privileges. Passing it cannot certify those capabilities.

The application reads batch2b/batch2c through service clients and an explicit company scope, after page-key authorization (`app/admin/operations/automation/page.tsx:33–38`, `lib/operations/batch2bAutomation.ts:266–281`, `batch2cAutomation.ts:338–355`). That application path does not exercise view writes, SQL locks or trigger DDL. Its absence of such calls cannot be converted into an undocumented migration requirement. No raw-SQL authenticated HTTP route or actual trigger exploit was demonstrated by this bounded review.

### Each non-SELECT capability, including the locking distinction

The same mapping applies separately to each of the three named views, accounting for all 21 non-SELECT additions.

| Privilege | What is and is not established on these actual view kinds |
| --- | --- |
| INSERT | Joined definitions are not automatically updatable. An INSTEAD OF trigger/rule could provide a write path. INSERT also permits explicit ROW EXCLUSIVE or less-conflicting SQL locks; it is not universally inert. |
| UPDATE | No current automatic view-update path. Existing SELECT/UPDATE rights can also support row-locking queries where PostgreSQL permits them. UPDATE permits any explicit table-lock mode. |
| DELETE | No current automatic view-delete path; DELETE permits any explicit table-lock mode. |
| TRUNCATE | A plain view cannot be emptied by TRUNCATE. Nevertheless this privilege is one of the grants that permits any explicit LOCK TABLE mode. Calling the ACL bit harmless solely because the relation is a view would be incorrect. |
| MAINTAIN | The ordinary view is not a materialized view or physical table that can be refreshed/vacuumed like one. MAINTAIN nevertheless authorizes any explicit LOCK TABLE mode. |
| REFERENCES | The plain view cannot serve as a foreign-key target. This does not add a valid view-backed FK in the reviewed schema; no new constraint/uniqueness behavior is established. |
| TRIGGER | Real DDL capability: permits creating/replacing triggers on the view when the function is executable. It can enable INSTEAD OF DML handling and cannot be treated as an inert grant. |

PostgreSQL 17 documents that locking a view recursively locks the relations in its defining query. For security_invoker=true, the caller must also possess the required privileges on underlying relations: the view does not supply its owner's lock authority. RLS row filters do not scope table locks to a tenant. This preserves the invoker privilege boundary, but does not prove harmless contention or equality to the reference ACL. [PG17 LOCK](https://www.postgresql.org/docs/17/sql-lock.html).

The joined-view DML limitation and security_invoker rules are specified by [PG17 CREATE VIEW](https://www.postgresql.org/docs/17/sql-createview.html). Applicable privilege meanings, including MAINTAIN and the special care needed for TRIGGER, are specified by [PG17 privileges](https://www.postgresql.org/docs/17/ddl-priv.html).

There is a concrete compatible existing function, not merely a hypothetical future trigger function: `public.set_updated_at_timestamp()` is invoker PL/pgSQL, sets NEW.updated_at and returns NEW (`supabase/schema.sql:48052–48060`; pinned bootstrap `20260522_set_updated_at_timestamp_foundation.sql:5–14`). All three views expose updated_at. Reference authenticated EXECUTE is explicit at schema.sql:113350; neither this function nor its grant has a delta in artifact 10394485748. Together with the added TRIGGER ACL this meets the documented privileges for attaching an INSTEAD OF INSERT/UPDATE trigger. Such attachment would change the catalog; invoking it could report a handled row without updating base rows. It does not itself demonstrate cross-tenant writes, arbitrary function creation, or an application-exposed SQL endpoint. Triggers do not fire on ordinary SELECT. [PG17 CREATE TRIGGER](https://www.postgresql.org/docs/17/sql-createtrigger.html).

This is a real increase in database capabilities, retained without a corrective migration because the inspected sources deliberately establish an invoker/client-role boundary but do not establish a contrary non-SELECT contract. It remains inappropriate to mark these 24 ACL rows equal to the reference or generically safe. If an explicit SELECT-only SQL contract is adopted later, the corresponding isolated repair would revoke all seven non-SELECT privileges on exactly these three ordinary invoker views, preserve SELECT/service/other ACLs, and refuse unreviewed column grants/dependencies. Its qualification must include actual trigger attachment and lock-mode controls, not only failing INSERT/UPDATE/DELETE or TRUNCATE statements. That would be a new least-privilege design decision, not a repair justified by inventing a September 4 service-only requirement for views.
