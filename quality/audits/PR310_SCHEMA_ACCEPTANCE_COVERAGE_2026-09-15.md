### Executable qualification and result interpretation

New fixed SQL: `scripts/sql/canonical-policy-actor-qualification.sql`; SHA256 `336e76fcdb4896c92f067750f71aebb60635b253385fb8a42e32bf1a946118f3`. The helper accepts only the existing admitted owned portable target or `NativeTimestampTarget`, requires the complete 144+514+4 receipt, pins the SQL and all 128 changed policy hashes, and checks catalog/row preservation after rollback. Parent native ledger admission and unchanged-ledger checks remain external gates.

The SQL creates rollback fixtures using the real retained `auth.users`, profiles, memberships, companies and platform-admin rows. It then uses actual `SET LOCAL ROLE` and JWT claim settings. It does not replace auth helpers. Eight actors are operations A, member A, operations B, disabled A, inactive-membership A, authenticated without membership, platform administrator, and service role. Six row-company cases are active A, active B, onboarding A, paused A, suspended A and NULL. This yields exactly **2,496 command cases** for the 52 identities.

The harness evaluates the **entire applicable permissive OR and restrictive AND**, including PUBLIC and inherited role applicability, against a typed synthetic row. It checks actual helper truth separately. UPDATE old-row USING and new-row WITH CHECK are checked independently; a correct USING cannot conceal an overbroad CHECK that permits reassignment. Effective table and column privileges are included. Direct and inherited authenticated ownership is rejected, as are authenticated SUPERUSER/BYPASSRLS attributes. This prevents the expression evaluator from pretending that bypassed RLS constrains the actor.

Service behavior uses its actual bypass attribute. Deliberate removal of redundant service policies must not cause a false denial where PostgreSQL actually bypasses RLS. The qualifier also rejects existing non-bypass, non-superuser principals inheriting service policy applicability. A successful receipt with `servicePolicyMode=bypass`, `servicePolicyRoleGraphClosed=true` and `serviceChangedPoliciesInert=76` supports **current-role inertness** of those exact 76 service-policy changes. It does not claim predicate equivalence or safety for future role grants. An evaluated non-bypass service receipt reports zero inert policies and leaves that semantic gate open. The context includes the exact 24-table union: billing-import batches/rows occur only in the changed service set; domain events/webhook deliveries only in the authenticated set.

This is policy-expression qualification, not business-table DML: it does not fire target triggers, satisfy every FK/check/default, prove event side effects, execute PostgREST, or validate server-action permission keys. Synthetic row attributes other than `id` and `company_id` are NULL; acceptance remains restricted to the reviewed company-based predicate families. A changed hash, unavailable helper, unexpected effective grant, actor mismatch or rollback difference blocks the run. No SQL source or acceptance expectation is automatically repaired.

The parent should retain the fixed SQL before replay staging, execute after the four forward effects and before catalog capture, and attach the successful receipt to the actual artifact. Failed qualification must not be represented as a successful final schema capture. For native execution, run only after full forward ledger admission and retain parent ledger checks before/after.

Independent code review resolved four concrete false-positive/negative risks: real service bypass, column grants, independent UPDATE components and inherited owner authority. The seven offline tests pass; they cover retained source admission, exact inventory/oracles, unowned-target rejection, receipt shape/types, partial/altered forward receipts, closed source/context/target-bound execution receipts and failed rollback. Native SQL execution has not been observed by this review.
