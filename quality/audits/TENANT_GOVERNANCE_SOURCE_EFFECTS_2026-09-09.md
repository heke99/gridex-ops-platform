## Atomicity, dirty state and synthetic verification design

Neither original contains top-level BEGIN/COMMIT. A DO/function invocation is a statement transaction under autocommit; its internal exception/rollback boundary does not include earlier successfully committed statements. `scripts/gridex-aud-003-clean-replay.sh:338–345` uses psql `-X -v ON_ERROR_STOP=1 -f` without `--single-transaction`: a later error stops execution but leaves earlier successful statements committed. A test that wraps a whole source in BEGIN proves only that wrapper's atomicity and is not evidence for the existing runner.

Example failure boundary, described without execution: a 6D profile check failure rolls back the shared membership/invitation/profile DO, while the preceding companies DO remains committed. A 6D2 late view column failure leaves user_roles UPDATE, journal, functions, policies, triggers and completion columns already committed under this runner. Successful repeated user_roles UPDATE is logically stable for status/is_active but can trigger timestamps/audit writes again. Repeating drops/recreates constraints and policies/triggers, so their OIDs need not be stable. Existing row PK/reference IDs, unrelated row attributes, retained FK/index identities and function/view identities should remain stable where the actual SQL promises them.

For implementation, use disposable databases and explicit preflight/catalog snapshots. If stronger source-level atomicity is proposed, make runner wrapping an explicit separately reviewed change with compatibility tests; never retrofit an unsupported rollback claim. Recover a failed disposable test from a clean clone or its documented committed boundary, not by silently continuing an unknown partial state.
