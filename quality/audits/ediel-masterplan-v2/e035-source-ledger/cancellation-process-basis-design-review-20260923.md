## What is addressed

- **Actual process grounds:** design lines35–59 require an independently originating correction confirmation, supporting process facts, typed erroneous-termination/end finding and explicit exclusion/holding of valid rescission/resumption. This distinguishes process cause from the C wire and from a mutable active supply row. HB26A pp46/93 supports the distinction; the counterparty-confirmation requirement is a conservative support rule, not a quoted national requirement for every cancellation.
- **Hash is not authentication:** lines27–41 separate retained bytes and DB hash from provenance, reject From/filename/self-authored assertions, and require independently retained channel/signature/contact evidence. Hash verification in existing `lib/customer-contracts/documents.ts:154–179` proves retrieved bytes match recorded metadata, not issuer authority; the proposal correctly does not promote that helper into an origin owner.
- **Reviewer is not caller-selected authority:** lines41,63 require authenticated actor context and a narrow interpretive permission. This deliberately goes beyond the current closure producer, which accepts reviewer input and checks communication/testing permissions (`lib/ediel/sources/reviewReceivedClosureSource.ts:21–32`); do not reuse that interface unchanged for process-basis authority.
- **Immutable causal chain:** lines28–31,65–67 require separate provenance and basis assessments/witnesses with no fallback to older acceptance. Line69 avoids the lifecycle deadlock of requiring the replacement closure before C's live-source=C check. Line71 retains independent endings and structural changes. These are appropriate corrections to the former design.
- **Honest implementation fixtures:** lines75–81 explicitly permit synthetic parties, real test roles, sealed test artifacts and actual assessment/witness operations. A supported verification producer must be implemented and exercised, not replaced by an arbitrary positive JSON receipt. No per-case external authorization ceremony is required.

## Important amendments

### C-PB-1 — Close the required Z08H/process-history universe

**Evidence:** design lines52,57 require resolving conflicting actual Z08H but describe history only as complete relevant matches from *available* owners, with completeness limitations. They do not define which owners are mandatory or whether a failed/missing required read prevents `positively_excluded` when a positive correction document exists. The current durable capture trigger only covers inbound PRODAT (`supabase/migrations/20260922095911_ediel_received_source_ledger.sql:93`), while the relevant Z08H is an outbound supplier rescission process (`lib/ediel/rulebook/businessSemantics.ts:193`; HB p70 links its LI/end to Z05L).

**Impact:** an implementation can query the existing inbound snapshot, retain a plausible positive correction document, and never discover an actual outbound valid Z08H for the target. Positive evidence must not silently override an omitted conflicting process owner.

**Required design change:** enumerate the minimal required internal readers/owners: retained outbound Z08H original and its actual dispatch/process state, inbound matching closure/C originals, and linked customer/contract/process records used to classify cause. Specify tenant/environment/customer/point/counterparty and initiator-scoped LI/end matching, broaden to unresolved potentially matching records rather than silently dropping malformed linkage, and use bounded exact-count reads with witnessed coverage/cutoffs. A required owner's failed/incomplete/truncated or unavailable relevant history yields a scoped unresolved outcome even with a positive document; genuinely irrelevant history is not a global blocker. State that finite database completeness is not universal real-world completeness. Add a positive-document-plus-conflicting-outbound-Z08H case and a positive-document-plus-failed-required-reader case. Implement missing producers/readers rather than inventing evidence or asking generic permission.

### C-PB-2 — Specify retroactive corrected-end support

**Evidence:** HB26A p93 expressly describes the additional supplier-contact requirement when a retroactive end change is necessary under the customer agreement. Design lines53,55,59 allow a supported corrected midnight and mention timing generally, but explicitly encode only the wholly erroneous supplier-switch dispatch deadline. They neither exclude retroactive corrected ends nor require the contact/necessity evidence for that exception.

**Impact:** an otherwise well-proven wrong-end claim could authorize a retroactive correction without the process condition in the cited source. A grid-owner document saying the prior end was wrong is not necessarily evidence that the required supplier contact occurred in connection with sending the correction messages.

**Required design change:** either explicitly hold retroactive corrected-end cases in this first slice, or add typed immutable evidence for customer-agreement necessity and the actual relevant supplier-contact event linked to the C/replacement process, with supported provenance and timing. Define prospective/retroactive using the process event and national time rule, not reviewer clock or DTM137. Keep the distinct supplier-switch deadline branch separate, using source-owned dispatch evidence and the explicit day-before-end rule. Test the selected support boundary; do not turn missing contact evidence into a national ERR.

### C-PB-3 — State the pending-boundary rule before the C witness

**Evidence:** design line69 describes the corrected-boundary blocker in the sequence ending with reviewed/witnessed C. The inherited cancellation design instead starts an unreviewed C's blocker at the old target stop. A corrected end can be earlier than the old stop even while both dates are prospective. The new design does not explicitly override that inherited lower bound at receipt/basis-before-C-witness cutoffs.

**Impact:** after correction evidence becomes visible but before C is witnessed, a reader following the inherited rule can still select positive coverage between the newly evidenced earlier end and the old end. The later C witness must not be the first point at which already visible unresolved correction context can block this interval.

**Required design change:** explicitly define selection at each cutoff: before any relevant correction evidence is available, retain the old saved view; once authoritative or unresolved potentially applicable correction context is visible, use the earliest proved/plausible affected boundary (including an earlier corrected end), or a scoped unknown-boundary hold when it cannot be bounded. Before C witness this is only a blocker, never restoration. After C witness, remove only the named old closure while retaining the pending corrected boundary and earlier independent bounds until the separate qualified replacement resolves them. Add an earlier-new-end positive fixture plus receipt/basis/witness cutoffs, with exact boundary sides. Preserve immutable prior snapshots and finalized retry outcomes.

## Design quality and qualification limits

No additional blocking provenance flaw is asserted merely because documentary review is human: the proposal labels it honestly and requires independent origin evidence. A human permission or checked confirmation cannot substitute for those records. The concrete implementation should choose at least one supported provenance method with an actual retained verification producer; all unimplemented alternatives remain unavailable.

The existing timeline's latest-revision and separate-witness machinery (`lib/ediel/sources/receivedSourceDecisionTimeline.ts:218–226`) is a useful model, but new provenance/process histories must participate explicitly; naming the existing snapshot does not include outbound histories automatically.

After the three bounded amendments, the owner can be implemented and tested using genuine synthetic end-to-end fixtures without pretending they are production evidence. This review does not approve production cases, whole E035, unrelated lifecycle branches or universal cancellation permission.

## Scoped amendment review — round 1

**SPEC: APPROVED. QUALITY: APPROVED at design level. C-PB-1, C-PB-2 and C-PB-3: ADDRESSED.** This supersedes the initial design-blocking verdict for the revised cancellation-process-basis design. It does not approve implementation, actual production evidence or whole-E035 completion.

- **C-PB-1 — ADDRESSED:** revised design lines59–71 enumerate mandatory outbound Z08H originals/dispatch/process revisions, inbound closure/C/replacement sources, and relevant customer/contract/process histories. Line67 requires exact-count reads plus actual retention coverage from process initiation through cutoff, not merely complete results from available owners. Failure/truncation/missing required retention holds even with a positive document. Lines69–71 retain potentially matching malformed records and specify both conflicting and positively unrelated outbound cases. This closes the omitted-outbound-history path without turning an unrelated record into a global blocker.
- **C-PB-2 — ADDRESSED:** lines73–79 explicitly exclude retroactive corrected-end exceptions in this slice and use authentic C/replacement dispatch evidence. The strict future-midnight subset is labeled as conservative support, not a national rejection rule. Unknown/equal/earlier timing cannot clear authority. The separate wholly erroneous supplier-switch deadline remains distinct.
- **C-PB-3 — ADDRESSED:** lines93–105 override the inherited old-stop-only bound. Raw/unreviewed/rejected/unwitnessed correction context participates in saved readsets; first visible relevant context creates only a blocker from the earliest plausible affected boundary. Before C witness there is no restoration. After it, only the named old edge is removed, while the pending corrected bound, independent earlier bounds and structural changes remain. The day30→day20 sequence explicitly exercises visibility before approvals and keeps old snapshots unchanged.
- **Dependent ordering — coherent:** line77 explicitly permits a conditional prospective basis before replacement dispatch exists, without clearing the pending bound. Line91 then orders basis witness, actual C reopening, C witness, and independent qualification of the replacement when its lifecycle state permits. There is no requirement to apply the replacement's legacy closure before C review. If the replacement original/dispatch evidence already exists, capturing and qualifying its timing is an evidence operation, not proof that its operational closure has already run; implementation must retain that distinction. The pending hold clears only after that exact new original passes its own timing and closure-owner checks (lines77,100,105). A fixture can therefore honestly retain a dispatched new original before C review while keeping the supply active/source=C until subsequent closure application/qualification; no fabricated source state or dispatch timestamp is needed.
- **Implementation proof to retain:** exercise both replacement-evidence-already-present and replacement-evidence-not-yet-present at C review. In the former, evidence capture must not prematurely overwrite the required live C state; in the latter, the conditional basis cannot remove the pending bound. Existing required lifecycle/cutoff fixtures cover the surrounding behavior, but neither variant should be replaced by an asserted successful marker.
- **New load-bearing findings in amendments: None.** Provenance production, immutable process readers and SQL/witness enforcement remain actual engineering work specified by the design; this approval does not assert those producers exist yet.
