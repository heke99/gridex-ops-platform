## Confirmed load-bearing direct-grant scope defect

The latest shared `gridex_actor_has_company_permission` is `20260902100000_rpc_surface_and_permission_scope_corrections.sql:108-153`. Its ordinary actor branch requires active membership in the selected company, then calls `gridex_get_user_permissions_in_company`. The latter's only implementation is `20260902091000_company_scoped_permission_engine.sql:149-212`, confirmed unchanged in the authentic schema snapshot `supabase/schema.sql:27237-27299`.

Its `direct_permissions` CTE at `:190-195` filters only `up.user_id` and the normalized permission key. It ignores `up.company_id`, `up.status`, `up.is_active` and `up.effect`. Concrete counterexample: actor U is an active viewer in A and B, with one active allow direct communication.send row bound to A and no role grants. The selected-company wrapper for B passes B membership, and the direct CTE returns A's permission, so capture of B's sealed original is authorized. A sole direct row with effect=deny, status=removed_from_company, or is_active=false also produces a positive permission. This is statically confirmed predicate behavior, not a claim of executed local SQL.

The existing wrong-company native case (`:81-91`) uses an actor with **no membership** in the other company, so it cannot detect this dual-member case. Existing limited-actor cases have a different key and do not exercise disabled/denied send rows. Materializing the missing registry keys alone would therefore leave a load-bearing tenant authorization defect.
