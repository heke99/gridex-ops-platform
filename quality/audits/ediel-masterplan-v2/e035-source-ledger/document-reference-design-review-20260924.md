# E035 reference-only document context design gate

Independent design-only review, 2026-09-24. Reviewed the proposed reference design, approved cancellation-process-basis design and amendment review, binding Task2 plan, actual document helper/API, archive lock migration and online/admin signing producers. No product/schema/memory edits, tests, commits, delegation or hosted operations. The concurrent sealed-Z05 capture author is unaffected.

**SPEC: NEEDS THE FOUR BOUNDED AMENDMENTS BELOW. QUALITY: APPROVE THE REFERENCE-ONLY DIRECTION, WITH THOSE CONTRACT DETAILS REQUIRED BEFORE IMPLEMENTATION.** A context-only immutable reference receipt is feasible without introducing a duplicate PDF byte-retention class. It must be explicitly a new, weaker context record, not satisfaction of the approved sealed-artifact/provenance prerequisite for positive C. No new retention permission or generic external approval is needed to design this hold-only owner.

## Confirmed foundations

The archive trigger rejects document deletion and locks company/contract/type/bucket/path/MIME/SHA/generation snapshot once storage_path is non-null. It does not lock verified_at/generated_at/archived_at and does not make storage objects undeletable. documents.ts uses upsert:false on its writer, but its existing-row shortcut and supplied digest are not readback proof. downloadAndVerifyCustomerContractDocument actually downloads and hashes bytes; SQL cannot independently perform that observation. The API guards tenant access before download, whereas getCustomerContractDocumentById alone is unscoped. Online and admin-import generation schemas identify different producers, neither of which proves correction cause. These distinctions in the proposed design are accurate.

Fresh byte revalidation, loss/timeouts yielding scoped unavailable, unknown inception coverage staying incomplete, and immutable old readset receipts are the correct limits. Hash verification proves byte identity, not issuer authority, cause, uninterrupted storage or permanent audit retrievability. No inference may promote a context receipt into correction-basis authority.

## Required amendments

### DR-1 — Fix capture size and bound retrieval

The proposed test says10 MiB+ rejection and the operation merely says bounded size. The binding Task2 plan sets **2 MiB (2,097,152 bytes)**. The existing bucket10 MiB setting is not the capture limit. Specify exact2 MiB acceptance and2 MiB+1 rejection, plus a10 MiB bucket-valid input being capture-ineligible. Enforce the limit on actual bytes, not MIME/metadata/Content-Length alone. The existing helper buffers the whole object before returning and has no operation-specific timeout; the new wrapper/read path must have a bounded download/time budget and reject oversized data without creating a verified receipt. This is a capture eligibility limit, not a change to archive retention or general contract-document upload policy.

### DR-2 — Name observation time separately from commit visibility

Replace ambiguous “server capture/commit time” and “post-commit availability witness” with separate contracts: storage read start/completion (server-observed hash/byte count), DB append transaction identity/server record time, and a later committed-row availability witness using the existing transaction-visibility architecture. SQL now()/a timestamp before commit is not proof that a row was committed at that time. The witness proves a committed receipt was observable, not PDF availability at commit or continuously since the read. If a second storage read is required, give it its own observation times/hash and still make no interval-continuity claim. Test delete/replace between byte read and DB append, between append and witness, and after witness; all new content-dependent reads revalidate and hold on loss. Preserve the earlier receipt as a statement about its actual observation only. Do not backdate knowledge from signing/verified_at or manufacture DB proof of object storage state.

### DR-3 — Make actor/SQL ownership enforcement explicit

The server interface correctly omits caller-selected actor and requires all three permissions plus operational-company access. State that it derives the authenticated actor from server context, persists that identity, and binds all source/document/contract/customer/site/point/supply references to the same allowed company and source environment. SQL must independently verify the full linkage and current actor membership/required grants at append, not accept a TS-asserted tenant graph or arbitrary actor UUID as authority. Private forced-RLS tables, no direct client/service DML, narrow service-only wrappers, closed shapes and append-only receipt/witness revisions must be explicit for this new table as they are in Task2. Contract documents have no automatic source environment authority: bind environment through the sealed source and target graph. If a link is absent/ambiguous, retain scoped unresolved context instead of inventing exact matching. Test wrong tenant, stale/revoked actor, another customer's contract, environment mismatch and direct-RPC/DML denial. Do not claim SQL independently authenticates a web session carried by a generic service-role connection; session derivation is the trusted server boundary, and SQL independently rechecks that derived actor's authority.

### DR-4 — Persist unresolved concern before successful byte verification is required

The prose promises rejected/unwitnessed visibility, but the operational sequence only specifies append after successful download/hash. Define a durable attempt/concern receipt after authenticated, tenant-safe source/document relevance is established, before storage retrieval can fail; append its verified/unavailable result separately. Alternatively specify an equivalent durable failure path and an explicitly incomplete reader when that recording fails. A missing PDF, wrong hash, timeout, oversized object or lost witness must not cause the selected relevant document to disappear from the process-history universe. Do not store foreign-tenant document details or create a foreign concern on an authorization failure. With no trusted corrected date, the unresolved concern holds the matching scope conservatively; it never invents a new boundary or clears an older hold. New cutoffs include raw/rejected/unwitnessed/lost-byte concerns; older saved snapshots remain unchanged. Add failure-before-append/interruption and unwitnessed/rejected visibility tests, not just successful reference lookup tests.

## Scope decision and retention

The approved process-basis design requires retained bytes for its authoritative artifact. A reference-only context receipt deliberately does not replace that requirement: mark its kind context_document_reference_v1 and make it ineligible for positive provenance/basis/C consumers by construction. It may later lead to a separately authorized sealed/provenance owner; that future work must qualify retention and actual evidence anew. For the present hold-only slice, underlying lawful document retention continues, actual observed coverage/gaps are recorded, and retention loss remains fail-closed. This is a narrower alternative, not silent weakening of the existing positive-C design.

After DR-1..4 are incorporated into the separate reference subtask/design, this direction can receive design-level SPEC/QUALITY approval. No reason was found to pause or broaden the independent sealed-Z05 Task2 implementation. These are specification amendments, not claims of executed implementation defects or requests for production evidence.


## Scoped amendment rereview — DR-1..4

**SPEC: APPROVED. QUALITY: APPROVED at design level for the weaker hold-only reference owner. DR-1, DR-2, DR-3 and DR-4: ADDRESSED.** This supersedes the initial amendment-required verdict above. No new load-bearing breakage found in the amended design. This is not implementation/native acceptance and grants no positive C, correction-cause or provenance authority.

- **DR-1 ADDRESSED:** exact2,097,152-byte eligibility,2 MiB+1 rejection and bucket-valid10 MiB rejection are explicit. Actual bytes/hash and cancellable bounded retrieval are required; absent safe budget/cancellation cannot yield a verified receipt. Existing bucket/retention policy is unchanged. Implementation must actually realize the stated bounded reader rather than assume a timeout around an uncancelled full-buffer download provides that bound.
- **DR-2 ADDRESSED:** storage read start/completion, DB transaction/server record time and later committed-row witness now have separate meanings. The design explicitly denies commit-time byte existence, uninterrupted retention and future availability claims; race/loss cases and immutable saved receipts remain required.
- **DR-3 ADDRESSED:** authenticated actor is server-derived, all three permissions and operational-company access are required, and SQL independently rechecks actor membership/grants plus full same-company graph/source environment. Forced RLS, denied direct DML, service-only wrappers, closed append-only revisions and caller/session trust boundary are explicit. Missing links remain unresolved; foreign document references are rejected without disclosure or foreign concern.
- **DR-4 ADDRESSED:** tenant-safe relevant attempts persist before storage access; unavailable outcomes append separately. Failure/interruption leaves the concern visible, initial capture failure makes the reader incomplete, and raw/rejected/unwitnessed/lost-byte concerns remain in newer cutoffs without rewriting older snapshots. The separate implementation must provide an actual completeness/failed-producer mechanism for the pre-attempt-commit case; a test asserting an in-memory flag alone would not satisfy this design.

The reference kind remains explicitly weaker than the approved retained-byte artifact and ineligible for positive provenance/basis/C. No new byte-retention class is created. Sealed-Z05 implementation continues unaffected. Rereview read only the amended design against the four recorded findings; appended only this review, with no product/schema/memory changes, tests, delegation or commits.
