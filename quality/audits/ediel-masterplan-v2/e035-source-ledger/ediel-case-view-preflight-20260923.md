## Decision and actual boundaries

Prefer a **single dedicated server page** `app/admin/ediel/operational-cases/page.tsx`, at `/admin/ediel/operational-cases` for a finite source-filtered list, and `/admin/ediel/operational-cases?caseId=<id>` for exact-ID detail. It keeps `app/admin/customer-cases/page.tsx` and its support-only predicate/action unchanged. An explicit `view=ediel` in Support is possible but couples a case-read audience to the existing `operations.tasks` support capability, its support creation UI and first-200-then-filter query. A separate one-page route is the smaller permission-safe behavior boundary; query ID is a real deep link, not a first-page selection.

- Page guard: `requireAdminPageKeyAccess('customer.cases')` (`lib/admin/accessModel.ts` accepts `cases.read` **or** `customers.read`). Control Tower uses `operations.control_tower` with a different OR-set. Do not silently grant either key to the other. In Control Tower, render a case link only if this context also qualifies for `customer.cases` (or is platform admin); otherwise show a nonlinked case summary and access explanation. `hasPermissionRequirement` is available in `lib/admin/accessModel.ts`. A communication-only Control Tower reader may see aggregate/summary but cannot follow case details.
- Resolve selected tenant with `resolveAdminTenantReadScope(context)`. If non-platform and `companyId` is null, show a no-company state and **do not call** service-client case/event/message/customer helpers. Platform null scope intentionally permits a read-only cross-company list/detail under its existing guard; show company identity on rows, no action forms. Never use a URL-supplied company ID as authority. `lib/customer-cases/db.ts` helpers are unscoped when company ID is omitted, so this gate is mandatory.
- The list query must filter `customer_cases.source = 'ediel_inbound_state_machine'` **in the DB before** its 200-row limit, with `company_id` for tenant readers, ordered newest first. Existing `listCustomerCases` has no source option and limits to 200 before a page-level filter. Add a narrow source-filtered helper or an optional source predicate to it (without changing default Support results). For `caseId`, call `getCustomerCaseById(id, scopedCompanyId)` separately; require exact source match before rendering anything, then `listCustomerCaseEvents(id, scopedCompanyId)`. Cross-company, non-Ediel and malformed IDs receive the same not-found treatment; do not load events first. No speculative case-platform abstraction.
- Detail renders writer's `reason_category` and validated `metadata.review_intent` (`lib/ediel/flows/inboundBusinessStateMachineLegacy.ts:257–288`), full title/description/`next_action`, priority/status, timestamps and existing scoped case-event messages. Treat metadata as untrusted JSON for display; label unknown/missing intent honestly, not as newly approved business authority.
- Source reference is `metadata.source_ediel_message_id`, **not** `cancellation_ediel_message_id`. Before showing even a permission-qualified source link, confirm the referenced `ediel_messages` row has `company_id === case.company_id` using a company-qualified lookup. Moreover `app/admin/ediel/messages/[id]/page.tsx:317` currently calls `requirePlatformAdminAccess()`; only platform-admin readers can actually follow `/admin/ediel/messages/<id>`. Tenant users get a text reference/"källvyn kräver plattformsbehörighet", not a dead or unauthorized link. This is a real product limitation, not an invitation to relax message-route RBAC. Validate the customer row's company before linking `/admin/customers/<id>`, and link only for `customers.read` or platform admin; that customer route uses its own `customers.detail` permission. Do not expose a cross-company link based solely on the case's customer ID.
- A dedicated `app/admin/ediel/operational-cases/actions.ts` status form, if offered, must independently require `cases.write`, explicitly reject platform-admin mutation, resolve and match the selected writable operational company (including the guard's selected-company identity), re-read the same-company case and enforce the exact Ediel source. Accept only the existing permitted triage statuses (the support action's finite set is a starting point; no source approval/market action). Reuse `updateCustomerCaseStatus` for company-qualified update plus `customer_case_events` and `audit_logs`, but protect against a source-reclassification race by adding an **optional** expected-source predicate to that helper's update, or an equally atomic source check. Keep its existing callers unchanged. Revalidate this page and Control Tower. The currently existing support action is not source-specific and its success copy says Support; do not reuse it directly for Ediel. `requireAdminActionAccess` permits platform admins and checks any writable membership, so neither it nor a hidden form field alone proves selected-company writability. `requireCompanyScopedActionAccess` additionally requires admin-class membership; decide deliberately if that would exclude legitimate cases.write operations agents, or validate selected membership status directly.
- Case triage is only a case status transition. It must not invoke `approveEdielInboundCaseAction`, message processing, ACK/sends, supply, billing or source-owner writes. Keep current writer, support API/portal contracts, RLS/grants, case-type/history and retry behavior intact.
