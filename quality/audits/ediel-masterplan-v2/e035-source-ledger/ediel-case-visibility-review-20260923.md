# Ediel review-case visibility — bounded independent finding validation

**Verdict: CONFIRMED Important navigation/follow-up gap; the stronger claim “the row cannot be seen or changed anywhere” is FALSE.** This is a separate bounded UI/read-path task, not a reason to change the current case-writer fix or remove support filters.

## Confirmed path and root cause

1. `lib/ediel/flows/inboundBusinessStateMachineLegacy.ts:257–290` creates review cases with `source='ediel_inbound_state_machine'`, typed `review_intent`/reason category, source message reference, description and next action. It does not mark them `support_case` or use a `tenant_support_` source. The current legitimate `case_type='other'` classification is not the visibility problem.
2. **Actual affected entry point is `/admin/controltower`, not `/admin/ediel/control-tower`.** `app/admin/controltower/page.tsx:93,100` counts and fetches all open customer-case rows in company scope. At `:122,135`, both the aggregate card and each recent row link to `/admin/customer-cases`, without the case ID or an operational-case view selector.
3. The destination deliberately serves support only: `app/admin/customer-cases/page.tsx:10–12,23–26` retains only `metadata.support_case===true` or a `tenant_support_` source. Its heading/copy expressly exclude normal operations. Thus the clicked Ediel row deterministically disappears even when recent enough to be in the first 200 rows. This is not a pagination-only issue.
4. No `app/admin/customer-cases/[id]` route exists in the route inventory. The generic `getCustomerCaseById`/`listCustomerCaseEvents` helpers (`lib/customer-cases/db.ts:110–127`) have no discovered admin case-detail consumer. The destination itself shows support descriptions/status actions but not Ediel case next action, source message link or event history. Fixing persistence alone does not establish the follow-up route.

**Reproduction from actual code:** an authorized company operator with switching.read and cases.write receives a same-company open Ediel review case. It appears in System Control Tower’s recent customer-case rows. Clicking that row loads the Support page, where the predicate excludes it. If this is the only case, that page reports no support cases. The operator cannot inspect that case’s next action or operate it from the advertised destination. No browser/native execution is claimed; this is deterministic traced source behavior.

**Business impact:** operational final-metering/billing, continuation, meter-change or masterdata follow-up is advertised but lacks a corresponding admin case investigation/triage surface. This can strand genuine work or encourage marking it handled from a summary without the underlying instructions. It does not itself grant market/source authority or prove a billing error occurred.

## Alternate surfaces checked — limits to the finding

- The `batch2c_drift_queue` includes unresolved customer cases (`supabase/migrations/20260521_batch_2c_end_to_end_operations.sql:378–391`). System Control Tower renders these with a “Markera hanterad” action (`app/admin/controltower/page.tsx:137`); `lib/operations/batch2cAutomation.ts:599–606` can mark the original case resolved in company scope. Therefore “no possible status update” is false. That summary supplies no case detail, source link or next action and does not repair the broken recent-case navigation.
- “Skapa driftuppgifter” is not an alternate case-detail viewer: `createCasesForBatch2CQueues` calls `ensureCase` (`lib/operations/batch2cAutomation.ts:523–548`), which itself inserts another `customer_cases` row (`:254–285`), with a non-support source. It does not turn the original into an accessible support case.
- `/admin/work-queue` uses the operational work queue and related task/events. The `gridex_work_queue_v` definition (`supabase/schema.sql:27235–27340`) contains blockers, information requests, grid-owner requests, operation tasks and supplier switches; it is not a customer-case detail projection.
- `/portal/arenden` really can show these rows: `listPortalCases` (`lib/customer-portal/db.ts:465–483`) selects same-company customer-owned cases without the support filter, and `app/portal/arenden/page.tsx:35–70` renders description/next action. This is an end-customer read surface, not an authorized staff case-triage/detail route. Do not claim absolute invisibility or treat customer impersonation as the intended operator workflow.
- No customer-case list/detail path was found in the checked admin customer-card or Ediel message/control-tower routes. Message review and immutable source approval remain separate functions; this finding does not imply those are inaccessible.

## RBAC and company constraints for a fix

- System Control Tower uses `operations.control_tower`; Support uses `operations.tasks` (`app/admin/controltower/page.tsx:82`; customer-cases page `:20`). These requirements differ: the former permits communication.read/partner_exports.read among others, while the latter requires switching.read/metering.read/billing_underlay.read/poa.read (`lib/admin/accessModel.ts:109–119,140–142`). A communication-only operator may be refused at the destination even before its support filter. Do not widen the destination blindly to all control-tower readers.
- There is already a case-read page capability, `customer.cases`, allowing cases.read or customers.read (`lib/admin/accessModel.ts:90`). Choose the intended finite review surface and align its links with its actual permission requirement. Writes must still require cases.write and active operational company authority. A visibility/status action must not grant provenance review, canonical source acceptance, market sends or cancellation authority.
- The current list/detail DB helpers use the service client and apply company predicates only when passed a company ID (`lib/customer-cases/db.ts:79–116`). Tenant read scope normally comes from the authenticated selected company; platform context intentionally yields null (`lib/tenant/adminScope.ts:10–20`). A new route must reject missing tenant scope for non-platform users before calling these helpers, qualify ID/events/source links by the selected company, and explicitly preserve any intentional platform read-only mode. Never interpret a URL company ID as authority.
- Existing status update adds `.eq('company_id', input.companyId)` (`lib/customer-cases/db.ts:380–390`), with an authenticated cases.write server action and server-resolved company (`app/admin/customer-cases/actions.ts:52–70`). Reuse these boundaries, not an unscoped service query or a client-selected actor/company.

## Smallest safe finite fix

Add an explicit **Ediel operational-case view** alongside the unchanged default support view (for example a validated `view=ediel` plus exact `caseId` selection, or a small dedicated route). Filter it by the existing authoritative writer source `ediel_inbound_state_machine`; display typed intent/reason, full description, next action, status and permission-qualified source/customer links. Include existing rows from that writer without requiring newly invented support metadata. Provide same-company exact-ID retrieval so a clicked older row is not lost behind a 200-row window. Keep actions as case triage/status only, with audit/event recording and existing write authorization.

Update Ediel row links in System Control Tower to the exact case/view; its row query must include the source needed to classify the link. Make aggregate labels/counts/destinations consistent (a separate Ediel card/view is sufficient for this finite task). Keep genuine support queries/UI/API/portal contracts unchanged. Do not solve this by relabeling operational cases as support or removing the support predicate. Other unsupported operational categories can be separately scoped; they are not a reason to broaden this fix into a general case platform.
