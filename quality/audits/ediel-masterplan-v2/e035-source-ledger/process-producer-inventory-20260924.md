## Exact minimum relational surface

Capture INSERT/UPDATE/DELETE old and new identity plus transition facts transactionally on these **named tables**. A trigger on each table covers SQL RPC, service/client direct DML, background batch and FK-cascade delete through that table; application callback alone does not. Scope to relevant process/customer/point after capture, never by treating a missing link as proof of unrelatedness. `company_id` is nullable on some older tables; a missing or conflicting tenant/object link requires rejection or durable unresolved gap, not tenant guessing. `created_by`/`updated_by` and event `source` are observations, not authenticated correction provenance.

## Atomicity, coverage, and remaining unsupported history

Each table's trigger must append the row transition/tombstone in the same business transaction, retaining OLD identifiers on DELETE. Oversize or identity-unbound relevant writes must either abort that mutation or commit an immutable scoped gap by an independently reliable same-transaction path. A post-commit callback or caught exception cannot satisfy this. A locked producer epoch per table and relevant SQL command precedes claims of coverage; read all included third-set rows, exact candidate counts, gaps and witnesses at the same MVCC visibility boundary as outbound/inbound sets. Apply the preflight's scoped 1,000-transition/65,536-byte-fact/6 MiB proposed limits; an overflow is `complete:false` for affected scope only. The archive path performs many individual transactions and deletes several tables, so capture each mutation and do not imply archive is one transaction.

**Concrete unsupported route:** `emitCustomerOperationEvent` deliberately swallows a failed insert, so no trigger on `customer_operation_events` can recover the omitted event. Capture its consequential contract/supply/switch/site/job/case transition at the actual DB table or canonical RPC; if an operational fact exists only in that skipped event, mark that interval incomplete until a genuine retained owner is qualified. External customer/counterparty communication or deleted pre-epoch event history also cannot be inferred from these tables. Future positive correction must still qualify the separately retained Task 2 correction document/process provenance and actual continuity; a post-epoch successful trigger deployment alone does not establish history from supply/process inception.

Implementation should verify the final database column spellings, triggers and route coverage at its exact head in native replay before moving the third set beyond partial. This inventory intentionally does not audit unrelated billing/notification producers or invent earlier absence.
