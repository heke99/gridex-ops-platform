# Successful retry binding — independent design gate

**Verdict: NEEDS CHANGES.** Full JSONB comparison against the existing immutable `raw_transaction` is a sound guard against changed QTY on replay, but is insufficient as the complete binding between successful persistence and actual legacy sink consumption. One confirmed Important/load-bearing design gap must be included in the implementation brief. This is a bounded design review, not implementation or whole-E035 approval.

## Confirmed gap: the RPC payload is not the sink projection

`lib/ediel/utilts/transactionPersistence.ts:85–113` builds `v_item` from `facts.transactions`. It stores local period strings, the resolution **value**, quantities, point/unit and other selected transaction fields. It does not include `resolutionFormat` or the message-level EDIFACT timezone.

The actual E66 sink input is different. `lib/ediel/utiltsEngine.ts:384–429` normalizes resolution using both value and format, selects energy quantities, computes observation periods and converts local periods with the timezone parsed from `facts.rawSegments`. `:432–460` independently normalizes the message-level billing periods and puts these transformed transactions in `normalizedPayload`. The public runtime returns this transformed payload at `:497`, while its original `facts.transactions` remain the persistence-builder input.

The legacy metering extractor consumes transformed period/resolution/read-time values at `lib/ediel/flows/utiltsDataRequest.part-1.ts:332–354`; billing consumes transformed top-level periods at `:678–693`. Therefore equality of all fields currently in `v_item` does not imply equality of the fields consumed by the sinks.

**Concrete counterexample:** preserve transaction quantities, local dates, transaction/point identity and disposition, but change only DTM+735 from a supported +0200 to +0100 timezone. The current persistence payload is identical, so the proposed raw-transaction equality and hash check succeeds. E66 normalized UTC periods/read times change by one hour. Billing month can also differ when the converted period endpoint crosses a month boundary (`monthAndYearFromPeriod`, part-1 `:67–81`, uses UTC month/year). This is a direct code-path proof, not an executed native replay claim. `resolutionFormat` is another omitted input to the projection; whether a particular alternate format remains accepted depends on its observation-count validation and needs a targeted valid fixture.

**Required correction:** bind the actual consumption projection or every input that determines it, rather than claiming the existing RPC JSON is that projection. At minimum cover normalized per-observation quantity/order, UTC periods/read time, normalized resolution/unit/quality, transaction and point/grid attribution, plus the message-level billing period and matching/request attribution used by billing. Immutable transaction quantity equality alone cannot establish the whole consumption contract.

## Can existing immutable series supply the missing authority?

**Not generally for E66 rows written by this RPC.** The existing columns are immutable, but they do not establish the missing UTC/resolution interpretation:

- `utiltsEngine.part-1.ts:445–454,502–517,627–645` parses local compact dates into strings without an offset and retains `resolutionFormat` separately.
- The builder sends those original local strings and raw resolution value (`transactionPersistence.ts:102–106`).
- SQL inserts `periodStart/End` by casting those offset-free strings to `timestamptz`, and stores the raw resolution value (`20260923113000_ediel_utilts_ack_plan_reservation.sql:148–156`). Those periods reflect the database session interpretation, not proof of the original DTM735 timezone used by the E66 consumer. A stored `resolution='1'` does not establish whether the original format was minutes/months/etc.
- Individual stored readings use `v_quantity.readingAt`, but the actual builder does not supply this field (`SQL:174`; builder `:108–113`). Those rows do not recover original normalized observation times.
- The immutable guard permits only `is_current` to change (`20260813124500_ediel_utilts_transactional_persistence_v1.sql:168–181`); immutability preserves the recorded data but cannot add missing semantics.

Existing series do provide authoritative raw quantities/order and recorded point/unit fields. A separately proven historical row format could be supported through an explicit compatibility adapter, but these E66 rows cannot universally be reinterpreted as canonical UTC consumption. Do not silently switch legacy sinks to these unqualified period columns, invent the missing timezone, or backfill historical authority from today's mutable message. Missing historical projection/source evidence must stop internally for review. An immutable original snapshot, if independently available and complete, could supply that evidence; its availability was not established in this review.

## Smallest coherent implementation specification

1. **Maintain the proposed authoritative comparison on both reuse paths.** For every persisted replay and insert-dedupe reuse, load the exact series under its company scope, validate a nonmissing object payload and its original SHA256 encoding (`digest(convert_to(raw_transaction::text,'UTF8'),'sha256')`), and compare typed JSONB content. Reject missing/corrupt authority. Validate the stored hash against the stored JSON; do not rely solely on a hash supplied by the caller. This covers existing raw-quantity mutation, including rows predating the fix.
2. **Add the missing consumption binding.** Before treating any persisted result as write authority, establish a versioned immutable consumption contract shared by persistence and both sinks. It must bind the normalized output and attribution actually consumed, or an immutable complete original source plus the relevant projection version/inputs. A single canonical projection produced before persistence and consumed unchanged afterward is one coherent approach. An origin marker or accepted/persisted flag is not sufficient. The source-wide billing period cannot be omitted just because per-transaction periods are present.
3. **Specify historical behavior explicitly.** Existing rows lacking proof for the complete projection fail internally without writes/ACK/completion. Do not fabricate a historical source seal or projection from current raw bytes. If identical old replay must remain allowed, that requires an independently authoritative prior source/projection or a proved complete legacy format; this review found neither for general E66 rows. New-format rows must support identical replay normally.
4. **Validate scope outside JSON equality.** `messageCode`, company, environment and source ID are RPC arguments, not fields in `v_item`. Validate incoming source family/direction/company/environment/message code; series company/message code/transaction identity and its originating source scope must agree. The current function checks family/company/environment at `SQL:34–38`, but not source message-code agreement. Cross-source dedupe may remain legitimate: require the same validated company/environment/code and complete content contract, not unconditional equality of series origin source ID with the current source ID. The existing dedupe key omits environment (`SQL:118–123`); prevent test/production reuse through explicit origin-scope validation or an equally authoritative environment binding.
5. **Keep conflicts internal and atomic.** Replay checks belong before returning success (`SQL:68–75`). Dedupe checks must not be swallowed by the existing `exception when others` (`:191–202`), which rewrites the reservation to ERR. Either perform authoritative validation outside that exception block while maintaining the series lock, or explicitly rethrow the dedicated internal-conflict class without touching reservations. This must roll back the entire batch, including any earlier accepted sibling insertion, and preserve pre-existing ACK/series/reservation rows. Genuine insertion failures retain their existing ERR behavior; evidence conflicts do not become national errors.
6. **Retain frozen outcomes and lawful corrections.** Keep non-held reserved disposition/response/issues immutable; held-to-accepted processing stays available where no prior durable accepted consumption exists. Identical, properly bound cross-source dedupe and genuinely new correction identities retain their documented behavior. Do not bypass comparison when `is_current=false`: an older successful source replay still needs its exact referenced immutable version.

## Focused acceptance evidence needed

- Retain the proposed native changed-QTY/identical/key-order/missing-hash/scope/dedupe/correction tests and real runtime no-side-effect conflict test.
- Add a real E66 parser-to-persistence-to-sink test changing only DTM735 while leaving today's RPC `v_item` unchanged. Demonstrate changed normalized periods first, then verify the completed contract blocks the retry before ACK/metering/billing/completion.
- Add qualified format/resolution and top-level billing-period cases, and a historical row lacking the new evidence that fails internally without trusting mutable current raw.
- Explicitly test an insert-dedupe conflict inside a mixed batch: no ERR reservation rewrite and no partial durable change. Include cross-environment source reuse despite matching current dedupe identity.

## Round 1 scoped design rereview

**Verdict: ADDRESSED — approved to implement this revised design.** This supersedes the design-blocking verdict above for `successful-retry-binding-design.md`; it is not a claim that implementation or qualification has occurred.

- **Timezone/resolutionFormat: ADDRESSED.** Design lines 9,27–32 place the builder after canonical normalization and explicitly bind both the omitted interpretation inputs and their resolved absolute observation outputs. Source-wide billing dates/month/year are independently included at line30. This closes the specific false implication that equality of old `v_item` proves equality of actual E66 consumption.
- **Shared consumption contract: ADDRESSED.** Lines 7–9,34,38–40 and60–64 require the same immutable, versioned, returned stored contract to supply both metering and billing; they freeze matching before persistence and forbid post-persistence payload/fallback rederivation. Billing sums accepted per-transaction contributions with a common bound billing context. Actor/source lineage is explicitly separated from reusable consumption content. There is no remaining design permission for an accepted/persisted flag alone to authorize a write.
- **Historical rows: ADDRESSED.** Lines 49,68–74 prohibit backfill from mutable current raw and prohibit treating offset-free old SQL periods as historical UTC proof. Unbound accepted/reserved rows fail internally without altering evidence; historical unbound held rows also require independently proven identity. New bound held rows can release through fresh structural evidence without changing original bytes/membership. This intentionally restricts old replay compatibility rather than pretending the missing evidence exists.
- **Replay, scope and dedupe: ADDRESSED.** Lines 47–54 qualify source family/direction/company/environment/code, verify exact referenced immutable versions and both hashes, and validate cross-source dedupe using equal content plus independently bound lineage. Cross-environment reuse is explicitly blocked despite the legacy dedupe key. Returned stored contracts must match prepared contracts before sink authorization, and the unbound old RPC cannot remain an alternate successful route (line44).
- **Internal conflicts and atomicity: ADDRESSED.** Line56 requires a dedicated internal conflict to escape catch-to-ERR, with whole-batch rollback and no ACK/fabricated rejection. Genuine insertion failures retain their distinct existing ERR behavior. Lines 51 and62 preserve frozen non-held outcomes and existing mixed-held consumption behavior.
- **Acceptance evidence specified:** lines 78–86 require actual parser/projection counterexamples, unchanged historical evidence, native replay/dedupe/batch rollback, real RPC-to-sink integration and no late fallback. The resolution-format cases explicitly respect actual validator outcomes rather than fabricating accepted invalid input.
- **New load-bearing design findings: None.** Implementation review must still verify these requirements are actually enforced, especially stored-contract consumption, historical failure paths and escape from the generic SQL exception handler.
- **Scope:** read the revised design and cited its numbered requirements. No broader code review, tests, code/index/branch changes or subagents. Only this requested report was appended.
