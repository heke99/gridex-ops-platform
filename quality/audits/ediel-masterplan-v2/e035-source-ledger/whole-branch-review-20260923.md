## Important findings

### R1 — P1: bound metering can reuse a row with different stored attribution or observation

New location: `supabase/migrations/20260923150649_ediel_utilts_bound_sink_authority.sql:168–185`, especially the unchecked delegation at 184–185. Relevant existing callee: `supabase/migrations/20260901165500_link_ediel_sources_during_atomic_metering_ingest_recovery.sql:42–68`.

The new wrapper validates and locks the **current** point/site/customer/request tuple and derives the payload from its immutable contract. It then calls `gridex_ingest_metering_value_atomic` and returns its result. That function's existing-row branch checks only `value_kwh` and `quality_code` once the canonical key matches. It links the incoming source to the existing metering/normalized row and returns that row without comparing its customer/site/customer-site/grid owner/request, resolution, readAt, reading type or normalized projection against the bound observation.

The key is company + point + period + register + product + direction + unit; it does not distinguish those other fields. A previously stored equal-value/quality row at the same key therefore remains authoritative even when its stored attribution/observation differs. Current-owner locks do not prove the ownership of that existing result. The customer/company foreign keys validate a referenced customer in the tenant; they do not equate the existing metering row's customer with the point's current customer. This permits a same-company ownership move or stale/colliding stored projection to attach a new source to the wrong customer's older result. A simpler drift case is a stored row whose resolution/readAt differs while value/quality/key remain equal. Environment-separated series are also insufficient when the downstream natural key omits environment.

False-positive check: followed the real bound sink, `normalizeAndStoreMeteringValue`, new SQL wrapper, and final legacy RPC definition; inspected relevant composite constraints. The new billing wrapper has an existing-result comparison, but there is no analogous metering result comparison. Existing native sink tests prove identical retry and current-owner drift, not a conflicting preexisting metering/normalized result at the same key.

Required correction: add a forward bound-metering boundary that locks and compares the reusable metering row **and its normalized projection** against all business-write fields of the stored contract before adding a source link or returning success. Preserve intentional multi-source lineage separately from reusable content. Reject conflicting existing content internally without mutation or response finalization. Do not edit historical migration bodies. Qualify equal legitimate reuse, differing stored attribution/observation, normalized projection drift, environment collision and retry after an already committed sink; include real SQL/HTTP assertions that source links and completion remain unchanged on conflict.

### R2 — P1: a mutable response flag bypasses existing billing verification and clears retry lineage

Location: `lib/ediel/utilts/consumptionSinks.ts:44–47`; input comes from `lib/ediel/flows/utiltsDataRequest.part-1.ts:509–522`. Completion writes are `lib/ediel/flows/utiltsDataRequest.part-2.ts:818–858`, particularly 847, and the later validated-message payload.

`createBoundUtiltsBilling` returns null whenever `dataRequest.response_payload.billingUnderlayId` is truthy. Consequently a completed retry, or an interruption after `syncGridOwnerDataRequestReceivedFromEdiel` commits but before ACK/final status, does not call `gridex_consume_utilts_billing_v1`. The full existing-underlay verification introduced in `20260923154221...` is bypassed. The mutable flag is not checked against the source or stored underlay. The processor then writes `billingUnderlayId: null`, reports not_created, and continues to ACK/validated success.

This is reachable without forging original bytes or bypassing persistence. The first successful pass legitimately populates the response flag. `syncGridOwnerDataRequestReceivedFromEdiel` merges explicit null into the existing response, so the lineage is actually cleared on retry. The native existing-billing tests interrupt **before** the completion call succeeds and mock that call; their request response remains empty. They do not cover this boundary.

Required correction: always obtain/verify the database-derived underlay for accepted writable contributors, including when the response already names one. Treat a response ID only as diagnostic or as a value that must match authoritative lookup. Preserve the verified existing ID in request/message/return state. Native/full-processor coverage must include completed replay, interruption after real completion before ACK, foreign or stale response ID, and changed existing underlay business fields with a populated response flag. Legitimate workflow/audit edits must remain allowed.

### R3 — P1: high-resolution exemption permits unsupported agency-89 quantities through the plain-ID matcher

Locations: `lib/ediel/utilts/structuralComparison.ts:33–43`, especially early return 38; `lib/ediel/utilts/qualifyReceivedStructure.ts:30–35`; actual consumer matching `lib/ediel/flows/utiltsDataRequest.part-1.ts:847–887`; contract authority `lib/ediel/utilts/consumptionPreparation.ts:52–69`.

The high-resolution energy-only exemption returns not_applicable **before** inspecting LOC identity/agency or legal-party scope. When all accepted transactions have this shape, qualification returns the unchanged accepted runtime without a source readset. The real UTILTS parser retains only LOC's first component (`utiltsEngine.part-1.ts:606–607,633`), and matching looks up that plain text in tenant metering-point aliases (`matching.ts:27–50`) without agency or issuer. Preparation then freezes this match as a writable consumption contract; persistence independently binds physical transaction membership but does not qualify the original LOC agency/issuer.

Thus an E30/E66 energy-only high-resolution transaction with `LOC+172+<existing-agency9-text>::89` can bypass the intended unsupported agency-89 hold and consume against the agency-9 point. This remains reachable under the A4 comparison-enabled window, so it is not merely the separately acknowledged prior-guide gap. The lack of meter/register comparison for energy-only data is legitimate; it cannot establish namespace/point ownership. The agency-89 design explicitly identifies this high-resolution consumer path as needing qualification.

False-positive check: followed the original LOC parser, transaction matcher, qualification call, preparation, immutable payload and SQL source-membership validator. No agency/issuer check is present in those write-authority paths. The existing high-resolution unit test asserts no source IO using an agency-9 fixture; the agency-89 structural test uses readings, so neither exercises the bypass.

Required correction: independently establish the bounded supported original identity before any high-resolution or policy-window exemption can authorize persistence/consumption. Until a positive agency-89 owner exists, hold unsupported identity scopes internally with response none and no consumable quantities; do not misreport E61/E62. The guard must cover both real processors and the immutable persistence contract, not just the comparator or a UI marker. Native/full-processor tests should mutate a valid original to agency89 with identical text, exercise the energy-only exemption and normal reading paths, and retain the supported agency9 exemption control.

### R4 — P2: a writable bound observation can fail review and still complete with a positive ACK

Locations: `lib/ediel/utilts/consumptionSinks.ts:27–39`, especially `if (stored.status !== 'stored') continue`; `lib/metering/normalizeMeteringValues.ts:105–108,181–185`; no-data-request success paths `lib/ediel/flows/utiltsDataRequest.part-2.ts:615–665,688–738`.

When ownership changes between persistence and the normalizer's read, immutable attribution mismatch returns `needs_review`. The bound adapter silently skips it. The permission/no-request path receives an empty metering list, generates the positive ACK, sets validated, and writes a success event saying values were stored. This can acknowledge a writable observation that was never consumed. A multi-observation pass can similarly omit a later observation after an earlier sink commit.

False-positive check: the database wrapper correctly throws on a race that reaches SQL, but this earlier TypeScript return prevents reaching SQL. The native ownership-drift test explicitly accepts either rejection **or fulfilled empty output**; it does not test the no-request completion/ACK path. This is not the legitimate contract capability skip: the caller already selected `metering.capability === write`.

Required correction: propagate non-stored outcomes for writable bound observations as an internal consumption failure/hold through the processor. No positive ACK/final successful completion may be produced from a partial or empty failed write. Preserve prior committed sink rows for idempotent retry. Add a real no-data-request/permission processor case with owner drift after persistence, and a sibling observation interruption; assert no success completion/ACK on failure.
