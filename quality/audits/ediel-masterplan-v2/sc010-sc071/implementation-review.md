## Confirmed first-snapshot findings

### F1 — P2: valid long purpose cannot be queued

`supabase/migrations/20261005101500_ediel_beneficiary_export_jobs.sql:15` restricts trimmed purpose to 512 characters. Existing `lib/ediel/services/limits.ts:3` and `projectionRequest.ts:35` accept purposes up to 2000 characters, and the existing assignment/grant path supports that limit. A valid active grant with the exact purpose of length 513–2000 passes the reused full filter but fails the new job INSERT constraint; the production route converts this into generic 403. The body/parser/SQL filter do not refute the finding because they explicitly allow this scope. Align the owned job constraint with the shared limit and verify at least a qualified 513-character positive boundary and the true maximum/overflow behavior. This is availability/contract incompatibility, not unauthorized export.

### F2 — P2: result-table wait can outlive the last lease check

Initial migration `:138–139` correctly checks `clock_timestamp()` after source/projection waits, but then `:144–146` INSERTs the private result and completes using that earlier `finished`. Acquiring the result table's RowExclusiveLock can wait (for example against a retained native diagnostic transaction holding ACCESS EXCLUSIVE). A lease valid at `finished` can expire during this destination wait; execution will then still insert and mark completed. The job's FOR UPDATE lock prevents a competing claimant from simultaneously reclaiming it, and the graph still protects grant revocation; those protections refute duplicate-worker and committed-revoke leak interpretations but do not make an expired token valid. Add a last wall-clock check after the potentially waiting result write, before completing, with atomic rollback on expiry. A native result-table wait/deadline probe should witness the actual wait and verify zero result/receipt writes after failure. A source-wait-only probe cannot cover this counterexample.

### F3 — P2: real role/endpoint policy denials remain leased and report infrastructure failure

Initial migration `:133` includes `ediel_current_captured_role_unavailable`, but the actual `require_current_source_role_v2` in `20260930231958_ediel_atomic_ack_owner_persistence.sql:42,46` throws **`ediel_ack_current_captured_role_unavailable`**. This helper is reached by the private filtered projection at `20261001015846...:245`. Its `:47` additionally calls `require_current_endpoint_v1`; that helper throws **`ediel_technical_endpoint_unqualified`** when the captured current endpoint eligibility is lost (`20260930184410_ediel_protected_technical_contrl_source_basis.sql:158,161` and following branches), also absent from the whitelist. A qualified job queued before captured role/profile or endpoint authority removal safely stops but rolls back to leased and the worker returns 503, rather than committing the plan's named blocked policy state. The generic exception rethrow is correct for corruption, receipt conflicts or unexpected infrastructure failures; do not replace it with a catch-all. Add only the actual reachable current-policy names, then prove real loss after queue and unchanged results/receipts/originals. SQL mocks of helper names alone cannot prove this classification.

## Lifecycle and other bounded observations

There is actual derivative cleanup, not just an expiry timestamp: claim deletes already expired results at `:108`, and read denies at `:161–162`. However cleanup runs only after active profile/membership/read-permission checks and only on that same actor's next worker pass. Payloads belonging to an actor permanently disabled or removed, or a tenant with no next pass, are physically retained indefinitely. Therefore the implemented guarantee is one-hour **read expiry plus opportunistic authorized cleanup**, not one-hour physical retention. No frozen SC010 card imposes a fabricated one-hour purge SLA; this is an explicit lifecycle limitation which requires either an independent coordinated expiry-cleanup path or truthful documentation. Job/audit references remain durable and no upstream original is purged by this consumer. Cleanup after revocation is distinct from permitting a cached read.

For a queued/leased job, read currently calls public projection before returning metadata with page null (`:159–165`); such an authorized status read can create a projection receipt before execution. Enqueue itself has no receipt effect, and actual denied reads throw inside SQL and roll back. Do not extend the witnessed no-receipt-at-enqueue guarantee to every pre-execution status read. This is a semantic observation, not proof of unauthorized output.

The result adapter `:55–60` trusts the service-only SQL page shape instead of repeating the synchronous projection adapter's whitelist/provenance validation. In the reviewed chain the SQL result is created only from the full filtered owner and cannot be caller-written; that refutes an asserted reachable arbitrary-JSON/raw-data leak. Optional transport validation is not a substitute for the actual SQL fence and is not an approval blocker by itself.

Existing projection grant/assignment temporal boundaries still use transaction `now()` (`20261001015846...:248`); the new lease uses wall clock. The wrapper does not independently qualify every inherited time-expiry boundary. This limitation was already stated in the design review and remains with the retained authority owner; this review does not infer that fixing a lease clock fixes those separate temporal semantics.

## Lock-order review and false-positive checks

All four new RPCs acquire the existing graph before acquiring new row locks. Execute/read then hold job before calling the existing source/assignment/grant path. Existing administration writer `20261001043917_ediel_service_source_network_period_timing.sql:67,93–96,131–147,169–180` takes its conflicting graph writer fence before source/assignment/grant writes and never touches the new job/result tables. Thus the proposed grant-writer-versus-job-row reverse cycle is not reachable in the reviewed current consumers. The existing graph's SHARE lock on grant/assignment and the writer's SHARE ROW EXCLUSIVE conflict serialize actual revocation until export commit, or make later export observe the committed revoke.

Enqueue validates source before its idempotent INSERT, but `ON CONFLICT DO NOTHING` against an already committed row merely locked by an executor is not a required row-update lock; treating it automatically as `FOR UPDATE` would manufacture a reverse source/job cycle. Claim cleanup deletes only expired completed results, while claim row selection covers queued or expired leased jobs and skips already locked jobs. Current completed read checks result/job expiry before taking a result FOR SHARE; no confirmed opposing wait cycle was found in these paths. These are source conclusions, not a native deadlock/race qualification.

Auth-body injection, global-superadmin/service bypass and cross-result IDOR claims were checked against trusted session fields, full SQL actor/beneficiary checks and immutable result scope. RPC `data` alongside `error` cannot override error in any adapter operation. Source/receipt corruption does not become a silent blocked grant in the initial explicit whitelist. Source details are not placed in worker or error responses. No successful unauthorized effect was established.
