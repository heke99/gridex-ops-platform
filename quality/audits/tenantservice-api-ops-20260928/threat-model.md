# Bounded tenantservice threat model — 2026-09-28

Scope: customer portal and external customer API, website sync, OPS customer actions, customer cases, billing inputs and their Supabase access. Runtime evidence is incomplete. This is a source-grounded starting model, not an ASVS certification.

| Boundary | Asset and attacker capability | Abuse path to verify | Current evidence and needed control |
| --- | --- | --- | --- |
| Tenant backend → Gridex API | API key, customer profile/cases; a tenant backend or stolen key can send identifiers | Select another end customer while retaining a valid tenant-wide scope | `externalApi.ts` authenticates integration client; `customerResolver.ts` accepts presented identifiers. Require separate issuer-bound delegated customer assertion, tenant/customer/resource binding and action-specific step-up for sensitive changes. |
| Portal login → server service role | Customer data and portal role; signed-in user can hold a stale session | Disabled account or another customer's link remains reachable through a fallback | `db.ts:getCustomerPortalContext` reads `is_active`; resolver now fails closed on disabled link for supplied user ID. Verify status, provider/issuer, revocation and direct database grants in an isolated DB. |
| OPS form → customer/contact/audit | Customer identity, billing destination; staff can submit stale forms | Overwrite concurrent changes or update legal/status fields while changing phone; partial contact/audit write | `profile-actions.part-1.ts` has sequential writes and full form fields. Require field policy, optimistic revision and one DB transaction with real actor attribution. |
| Case writer → customer portal/webhook | Internal notes, verification hints and personal data | Internal `next_action` or description becomes visible as customer content | `support.ts` and `customer-portal/db.ts` select/publicize internal-looking fields. Build explicit public messages and attachment visibility at write/read/export boundaries. |
| API retry → DB transaction/outbox | Monetary/profile correctness | Crash after business mutation creates retry conflict, duplicate case or missing outbox | `strictRequest.ts` uses a separate idempotency claim/completion; `support.ts` checks then inserts cases. Require unique claims and business/outbox result in one transaction. |
| Database Data API/RPC → tenant rows | Cross-tenant data and privilege state | Direct low-privilege call bypasses an HTTP guard | Service-role clients appear in these server modules. Inspect actual grants, RLS, views, SECURITY DEFINER functions, storage policies and direct RPC behavior before asserting protection. |

Prioritize cross-tenant access, portal takeover and internal case exposure as high-impact candidates. Actual likelihood and severity remain open until controlled reproductions and deployment configuration are checked. No active penetration test, external provider call, production migration or live customer action was performed. Use the official [ASVS 5.0.0](https://owasp.org/projects/asvs/) requirements as the control mapping target during P7; this document covers only the named trust boundaries.
