## Implementation

- Nine route modules mount the list/create/detail, replies, notes, calls, status,
  assignment and attachment list/upload/download adapters.
- Require explicit `staff_cases.read`/`write` plus `cases.read`/`write` through the
  shared staff context. Company comes only from that context.
- Resolve opaque case references within the company. Support marker, support
  source, `other` case type and absence of operational/billing/cancellation flags
  are required before reading or changing a case. List filters run in SQL before
  pagination; cursor resource includes company and active filters.
- Reuse createTenantSupportCase, replyToCustomer, addInternalNote,
  recordPhoneInteraction, updateCustomerCaseStatus and attachment commands.
  Existing OPS and customer defaults remain unchanged.
- Staff writes carry the actor and client in the idempotency fingerprint. Staff
  case creation additionally namespaces its existing domain idempotency key by
  actor/client. The shared support command delegates staff creation to one SQL
  transaction for case, first event, audit and opaque public reference, before
  any cached-case lookup. The generic non-atomic creation path rejects staff
  support before writing.
- Events and case/audit metadata identify `staff_api`, actor and API client.
  Staff create/event/status/assignment SQL transactions are supplied by S1; their real
  database behavior is not proved by this package's in-memory RPC seam.
- Explicit DTO projections omit raw metadata, customer/company identifiers,
  storage paths and arbitrary event payload. Staff user IDs are intentional.
  Internal notes/calls remain hidden from the existing customer projection.
  Events and attachments have stable keyset pagination (newest first),
  addressable history endpoints, and continuation metadata in case detail.
  Cursors bind company, customer, case and resource; invalid cursors return 400.
- Uploads are bounded to 4 MiB and reuse existing content inspection/quarantine.
  Downloads use staff audience, verified bytes and private no-store headers.

## Remaining integration gates

S1 must provide the agreed atomic create/event/status/assignment RPCs, support-reference
backfill/index and staff attachment audit trigger. S3 supplies customer reference
resolution, and root supplies context/HTTP helpers and staff create failed-key
recovery allowlist. The additive events machine-auth migration was created with
`supabase migration new staff_case_events_api_auth` as
`20261004090602_staff_case_events_api_auth.sql`; exact reviewed wrapper content
was moved into the CLI-created file. Root owns manifest and native CI wiring
for `scripts/staff-case-events-api-auth-regression.sql`. Frozen S1 source is unchanged. S5 owns OpenAPI and registry. Generated database artifacts,
real native SQL regression, full Vitest/build and exact-head CI are parent-owned
integration gates. No publish, merge, deployment or production mutation was
performed by this package.

The requested existing idempotency pattern has separate claim/business/receipt
transactions. After a successful business write with a lost receipt response,
non-create mutations refuse the failed key; no unsafe automatic repeat is added.
Existing attachment Storage lifecycle behavior is reused without a new lease
subsystem.
